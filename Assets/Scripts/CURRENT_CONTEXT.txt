Refined Plan: Asteroid Generation, Resources, Mining, and Fracturing (v1 “pixel-truth” design)

This document defines a restart-friendly, coherent design for:
•  Procedural asteroid generation
•  A resource system where each asteroid pixel == 1 resource unit
•  A mining loop where mining removes pixels, yields resources probabilistically, and can fracture asteroids
•  A fracturing system that remains stable, performant, and deterministic
•  Resource “quality classes” driven by pixel brightness / quality scalar

This is written as a design spec, not tied to the current code state, so you can revert cleanly and re-implement in stages.



0) Goals & non-goals

Goals
1) Pixel truth: Each solid asteroid pixel represents exactly one resource unit.
2) Deterministic: Given an asteroid seed + same profile preset, the resource distribution is reproducible.
3) Mining is intuitive: Drill removes material at the contact point. If you mine a chunk away, it’s gone.
4) Performance: Avoid heavy per-tick collider regeneration and avoid costly CPU per-pixel rendering at runtime.
5) Extensible: Resources can evolve (new resource types, new quality tiers, different distributions) without rewriting core loops.
6) Tunable: You can create Scriptable presets for resource makeup and quality distributions.

Non-goals (for early versions)
•  Perfectly physically accurate stress simulation.
•  Continuous real-time polygon collider regeneration every tick.
•  Complex vein shaders, bloom, or post-processing.
•  Full-blown inventory/production chain (we just need mining → storage path).



1) Data Model

1.1 Resource definition (authoring)
Resource is a ScriptableObject: name, color, weight, etc.  
Weight is constant across quality classes (per your requirement).

Key fields (suggested):
•  string displayName
•  Color baseColor (used for UI, tint, minimap, debug overlays)
•  float weightPerUnit (same across quality)
•  Optional: rarity / UI icon / tech flags (not used by mining logic directly)

> Important: Resource ScriptableObjects define type only. Quality is per-pixel.

1.2 Resource quality / classes
Quality is a per-pixel scalar quality01 in [0..1], but with your display constraint:
•  Floor displayed quality at 0.1 (so it never looks fully black)

Resource classes
You want 5 classes initially:
•  raw, rough, rare, refined, pure  
…but names/count should be flexible.

So: author a ScriptableObject ResourceQualityConfig:
•  List<QualityTier> where each tier has:
◦  string id (stable key, e.g. RAW)
◦  string displayName (e.g. “Raw”)
◦  float min01
◦  float max01

Example default:
•  [0.0–0.2] raw
•  [0.2–0.4] rough (or rare depending on naming)
•  [0.4–0.6] rare
•  [0.6–0.8] refined
•  [0.8–1.0] pure

(Your earlier text had “0.2–0.4 is rare” but also mentioned “rough”; this config resolves that cleanly.)

Rules
•  All tiers have the same weight (weight is per unit, independent of tier).
•  Tier impacts are gameplay/market/UI decisions later.



2) Asteroid Resource Representation (“Resource Map”)

2.1 Core representation: pixel map
Each asteroid has a generated texture rockTex (RGBA) that defines shape:
•  alpha > threshold = solid pixel
•  This is already how your asteroid textures work.

We add a parallel resource payload representation. There are two good options:

Option A (recommended): CPU-side arrays + optional texture for debug
Maintain:
•  byte[] resourceTypeIdPerPixel (size = w*h)
•  byte[] quality01PerPixel (0–255, size = w*h)
•  BitArray or alpha check for “solid vs empty” can be derived from rockTex.a

This is the authoritative truth used by mining and fracturing.

Optional: build a debug texture from these arrays for editor visualization (not required at runtime).

Option B: encode into a second texture
Maintain a second texture resourceTex where:
•  R channel encodes resource id (0–255)
•  G channel encodes quality (0–255)
•  A channel encodes solid (or rely on rock alpha)

This can simplify GPU visualization, but you do not want shaders right now; so Option A is better initially.



3) Asteroid Generation Pipeline

3.1 Inputs
•  seed
•  geometry parameters (size, noise, etc.)
•  AsteroidResourceProfilePreset (ScriptableObject)
•  ResourceQualityConfig (ScriptableObject)

3.2 Output
•  rockTex (visual sprite texture)
•  filledPixelIndices (or count)
•  resourceTypeIdPerPixel[]
•  quality01PerPixel[]

3.3 AsteroidResourceProfilePreset (the “composition” authoring)
This preset is the main authoring tool.

It should specify:
Composition (resource fractions)
A list of entries:
•  Resource resource
•  float fraction01 (share of all solid pixels; should be normalized)
•  Optional future: “vein-ness” / clustering param

Important: because BLACKSTONE is the base rock and mineable too, BLACKSTONE can be included in the fractions OR implicitly fills remainder.

Quality distribution per resource
Replace “concentration slider” with a curve:
•  AnimationCurve qualityDistributionCurve per resource OR a shared default curve with per-resource overrides.

How it works:
•  Sample u ~ Uniform(0..1)
•  Map to quality01 = curve(u)
•  Clamp to [0.1, 1.0] for display floor (or store true quality but display floor at render/UI time)

Default curve: “right-skewed” (lots of low quality, fewer high quality).
This can be achieved by a curve like:
•  y = x^k with k > 1
or an AnimationCurve that approximates it.

Determinism rule
All sampling must use a deterministic RNG seeded by:
•  asteroidSeed
•  and stable offsets (resource index, pixel index, etc.)

3.4 Assigning resources to pixels
Given a filled pixel list:
1) Shuffle filled pixel indices deterministically using seed.
2) Allocate counts per resource:
•  count_i = round(fraction_i * filledCount)
•  Fix rounding drift by distributing remainder or forcing last resource to fill remaining.
3) For each pixel assigned resource type:
•  assign resourceTypeIdPerPixel[p]
•  assign quality01PerPixel[p] using that resource’s quality curve

This is fast enough at generation time (not during chunk load, not during mining tick).



4) Mining System (Strategy 1)

You chose Strategy 1:
•  Mining removes pixels
•  Collider updates are throttled, not per tick
•  Mining yield is probabilistic per pixel removed

4.1 Digger stats
Recommended digger parameters:
•  tickIntervalSeconds (time per tick)
•  pixelsPerTick (how many solid pixels removed per tick)
•  brushRadiusWorld (world space radius of mining brush)
•  yieldChance (0..1) chance that a removed pixel yields resource into cargo
•  drillVolatility (renamed from digForce): adds extra damage / instability per tick (optional)
•  Optional later: targetHardness, heat, etc.

Interpretations
•  Removing pixels is “material excavation” (always happens when you mine actual solid).
•  Yield chance is “how much gets captured vs lost as dust”.
•  Volatility is “how much you destabilize the body beyond just removing material”.

4.2 Mining tick algorithm
Each tick for each digger contact:
1) Determine contact point in asteroid local space.
2) Convert to pixel coords.
3) Collect candidate solid pixels within brush radius.
4) Choose up to pixelsPerTick pixels (deterministically or pseudo-randomly).
5) For each chosen pixel:
•  Remove it (mark solid → empty; alpha to 0 in rockTex or separate mask)
•  With probability yieldChance, add (resourceType, quality) to results list
•  Apply destabilization: lower asteroid break threshold based on pixel removed (see below)

6) Update visuals:
•  For no shaders: you can update rockTex alpha and Apply() periodically
7) Update collider throttled:
•  If removedPixelsSinceRebuild > threshold OR timeSinceRebuild > threshold:
     rebuild polygon collider from updated texture

4.3 Prevent “mining air”
Mining must only remove pixels that are currently solid.  
If no solid pixels in radius → nothing happens.

So even if collider is stale, mining logic remains correct.

4.4 Collider throttling policy
We need to avoid heavy runtime collider generation while also avoiding long-lived “ghost collision” areas.

Recommended policy:
•  Rebuild collider when either:
◦  pixelsRemovedSinceRebuild >= 75 (tune)
◦  OR timeSinceRebuild >= 0.75s (tune)
◦  OR “surface breach” detected (if you implement “hole reaches outer boundary”, rebuild immediately)

This keeps physics “mostly” aligned without constant spikes.



5) Structural Damage & Fracturing

5.1 Destabilization-from-mining (fracture without volatility)
You want asteroids to fracture even if drill volatility is 0, because removing pixels is structural.

Model:
•  Initial break threshold is computed as today (mass * toughness).
•  Define breakThresholdPerPixel = initialBreakThreshold / initialSolidPixelCount
•  Each removed pixel reduces break threshold:
◦  breakThreshold -= breakThresholdPerPixel

This guarantees that removing enough of the asteroid will eventually drop breakThreshold to a point where it fractures (or reaches zero / empties).

5.2 Drill volatility (optional extra damage)
Volatility is the “unsafe” part:
•  Each tick (or each removed pixel) can add extra accumulated damage:
◦  accumulatedDamage += drillVolatility per tick
◦  or += drillVolatility * pixelsRemovedThisTick

Interpretation:
•  High volatility fractures asteroids sooner, which you don’t want because fracture yields nothing (in your current direction).

So players optimize for:
•  low volatility
•  high pixelsPerTick and high yieldChance
…but those can be balanced by tool design.

5.3 Fracture yields
You stated: fracturing yields nothing; resources come from mining ticks.

That implies:
•  Fracture is primarily a “failure mode / hazard” or “mechanical consequence”, not a reward event.
•  Collision fracture becomes a way to “waste” ore (destroy without collecting).

This is coherent with yieldChance being the only way to capture resources.

5.4 What does fracture do physically?
When fracture triggers:
•  Use your existing Voronoi fragmentation to create fragment textures/colliders
•  The fragment textures must inherit the removed pixels (holes) already applied
•  Ideally: resource maps should split too (not required immediately if you only mine pre-fracture and fracture yields nothing; but for consistency, you should propagate remaining pixels)

If you want to keep it simpler initially:
•  When fracture happens, just destroy asteroid and spawn fragments visually/physically (resources not spawned).
•  Later: propagate resource maps to fragments so you can keep mining fragments.



6) Resource Storage & Return Types

6.1 What mining returns
Mining returns a list of “units”. Each unit is a pixel:
•  resource type
•  quality01 (or tier id derived from quality config)

So define a struct/class:
•  MinedResourceUnit { ResourceEnum type; byte qualityByte; }
or in C#:
•  public struct MinedResourceUnit { public ResourceEnum type; public float quality01; }

Then:
•  BrokenResourceData should evolve from List<ResourceEnum> to List<MinedResourceUnit>.

This is a key part of the restart plan: the current BrokenResourceData is too small for quality.

6.2 Cargo system
Cargo should store resource units (including quality), not just enums.
But if you want a v0 compromise:
•  store only enum for now
•  track quality later

Given your new direction, better to encode quality now.



7) Visuals (minimal, no shaders)

You do not want custom shaders right now, but you still need to debug and read resources.

Minimal visualization plan:
1) Asteroid base texture already exists.
2) When generating the asteroid, tint pixels by resource color and apply brightness based on quality.
•  This is done once at generation time (acceptable).
3) When mining removes pixels, you only need to clear alpha of those pixels, and occasionally Apply().

This is CPU texture editing, but constrained:
•  Generation: one-time full texture write
•  Mining: small brush updates per tick (only a handful of pixels), then Apply() maybe throttled (every N removed pixels)

This should perform far better than extra shaders/material churn if your bottleneck was material/shader overhead or GPU.



8) Determinism rules (important)
To prevent “random drift”:
•  All pixel assignments and quality assignments use deterministic RNG seeded by:
◦  asteroidSeed
◦  stable offsets: resource index, pixel index, etc.

Example:
•  resource assignment: shuffle filled indices using seed
•  quality assignment: rng = new Random(seed ^ pixelIndex ^ resourceId * 1315423911) etc.

This ensures the same asteroid regen produces the same map.

12) Summary of the final conceptual model

•  The asteroid is literally a 2D grid of resource pixels.
•  Each pixel has:
◦  resource type
◦  quality scalar (brightness)
•  Mining removes pixels around the drill contact point.
•  Each removed pixel:
◦  always disappears
◦  yields loot with probability yieldChance
◦  reduces structural stability (lowers break threshold per pixel removed)
•  Drill volatility is extra “unsafe damage”, encouraging low volatility for maximum yield.
•  Collider rebuild is throttled to avoid lag.
•  Fracture is a physical event, not a reward event (no fracture yield).
